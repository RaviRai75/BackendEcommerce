# Historical, owner-scoped customer exchange requests

Task 21 adds placement-time exchange entitlements, owner-only eligibility and request APIs, customer evidence uploads, and an immutable `REQUESTED` exchange aggregate. Policy and product eligibility are captured only when an order commits; full-line source/replacement facts and current same-product/same-colour size choices remain server-derived. Creation rechecks the order, entitlement, replacement, and evidence inside a transaction coordinated with media reclamation. **Watch for:** **confirmed** audit loss after a successful commit, **confirmed** duplicate-line responses changing to 503 when transaction support is unavailable, and **confirmed** missing integration coverage for customer upload completion and exchange-evidence reconciliation.

**Verdict**: NEEDS_CHANGES

## High-level view

Placement captures a random line token and fixed-key policy snapshot. Missing or invalid policy data persists an ineligible snapshot rather than blocking checkout, preventing later catalogue or policy changes from granting historical entitlement.

Customer routes remain owner-bound even for administrators and expose explicit DTOs without MongoDB identifiers. Creation writes no order history, stock, reservation, fee, refund, QC, or logistics state.

Creation requires transactions and shares the catalogue/media write guard. **Confirmed:** transaction availability is checked before duplicate-line detection, so a new key for an already-requested line returns 503 instead of `EXCHANGE_ALREADY_REQUESTED` when transactions are unavailable.

Exchange evidence is image-only and purpose-bound, with attachment serialized against orphan reclamation. **Confirmed:** tests do not drive customer upload completion or prove that reconciliation removes unattached exchange evidence while retaining referenced evidence.

The exchange and its audit record are separate commits. **Confirmed:** an `EXCHANGE_REQUESTED` audit failure after the exchange commit produces an error, and exact replay never repairs the missing audit.

## Idempotency and duplicate-line semantics under topology loss

Existing idempotency keys are resolved before transaction support is checked, preserving replay and changed-body conflict behavior during a topology downgrade. A new key for an existing line instead reaches `supportsTransactions()` before the owner-bound duplicate lookup and returns 503 immediately. This is **confirmed** in `exchange.service.js`, where duplicate detection occurs only inside `withCatalogueWrite` after the topology gate.

Preserve idempotency-key precedence, perform an owner-bound duplicate preflight before the transaction gate, and retain the transactional recheck for races. Add a case that creates an exchange, disables transaction support, and expects `EXCHANGE_ALREADY_REQUESTED` for a new key without further writes.

## Audit durability after a committed request

`auditRequested` runs after `withCatalogueWrite` has committed the Exchange. This **confirmed** failure path leaves a durable exchange without its required event: the initial request fails on the audit insert, then exact replay exits through `replayResult` without retrying the audit.

Make the exchange and audit one durable outcome by recording the event in the transaction or using a transactional outbox. If post-commit audit writes remain, exact replay must idempotently detect and repair a missing event.

## Exchange evidence completion and reclamation coverage

The new tests never call `POST /api/media/exchanges/uploads/complete`; this missing coverage is **confirmed** in `exchange.test.js`. Media reconciliation tests cover `HOME_HERO` and `COLLECTION`, but none creates an old `EXCHANGE_REQUEST` asset or an Exchange photo reference.

Add customer completion success plus anonymous, foreign-owner, and wrong-purpose rejection cases. Add reconciliation cases proving that an old unattached exchange asset is reclaimed after the grace period and an asset referenced by `Exchange.photos.assetId` is retained.
