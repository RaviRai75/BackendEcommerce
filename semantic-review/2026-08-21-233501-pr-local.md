# Versioned normal-order fulfillment with durable action acknowledgements

Task 23 adds a closed ADMIN fulfillment state machine, transaction-coupled manual shipment tracking, customer-safe tracking projections, and atomic pre-shipment cancellation. Action responses are assembled inside the mutation transaction and retained through known or marker-reconciled commits, while ordinary Order/Shipment joins use bounded Order-version rechecks. The prior courier namespace, transaction-population concurrency, and silent 500-customer search truncation findings are resolved. The replacement search preserves completeness but introduces an unbounded application-memory and MongoDB command-size failure mode. **Watch for:** **confirmed (medium)** broad valid ADMIN `q` searches can exhaust memory or exceed MongoDB's BSON command limit before pagination is applied.

**Verdict**: NEEDS_CHANGES

## High-level view

The six ADMIN actions form a one-way Order lifecycle guarded by `expectedVersion`. Order mutation, Shipment creation or advancement, cancellation release, and strict audit creation share one snapshot transaction; ambiguous commits are majority-reconciled by a private action marker and return the DTO created by that transaction.

Ordinary customer and administrator detail reads accept an Order/Shipment projection only if Order retains the same `__v`. Every D32 shipment change increments Order `__v`, closing the mixed-lifecycle response race without placing ordinary reads in transactions.

Manual shipment identity derives a normalized `courierKey` and uniquely scopes AWB, tracking ID, and private shipment ID by courier, while retaining the one-forward-shipment-per-order fence. Customer projections omit private identifiers, actors, reasons, and reconciliation markers; ADMIN routes use database-backed authorization and private non-cacheable responses.

ADMIN search no longer silently drops customers after 500 matches. It now reads every matching User ID into Node and embeds the complete set in the Order filter, so broad terms are unbounded before the requested Order page limit takes effect.

## Customer-backed ADMIN search is complete but unbounded

**Confirmed — medium.** `adminFilter` executes an unrestricted User query for name, email, or phone matches, materializes all matching `_id` values, and inserts them into a `$in` predicate used by both the paginated Order query and `countDocuments`. Pagination cannot bound this preliminary query. A broad valid term can create a large application allocation and eventually exceed MongoDB's 16 MiB BSON command limit, turning an ordinary admin search into a failed request.

Move customer matching into a database-side join/aggregation that paginates Orders without constructing an application-side ID set, or narrow the accepted search contract to an indexed exact customer identifier. Do not restore a hidden result cap, because that would make the page and total incomplete again. Affected symbol: `adminFilter` in `src/modules/orders/orderFulfillment.service.js`.

</details>
