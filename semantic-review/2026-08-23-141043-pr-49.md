# Atomic password and credential-epoch invalidation

Password reset and authenticated password change now update `passwordHash` and `tokenVersion` in the same atomic User write, then use a private session sweep that does not bump the epoch again. The public `revokeAllSessions` contract remains bump-before-sweep for logout-all, refresh-token reuse, and account suspension paths. Change-password adds a compare-and-set guard over the verified hash and epoch, while reset retains its reset-generation claim. **Watch for:** no blocking concern found; the credential epoch, refresh race, reset generation, audit, and API-error boundaries were traced with **confirmed** confidence.

**Verdict**: APPROVED

## High-level view

Reset and change commit the new password and authentication epoch on one User document. A failed or delayed Session sweep can leave stale rows in storage, but the old access and refresh credentials carry the prior epoch and cannot authenticate.

The helper split preserves two contracts: public `revokeAllSessions` owns the epoch bump, while password flows call the private sweep after their atomic bump. Refresh reuse retains bump-before-sweep ordering and rotation retains its post-successor epoch check.

Change-password makes the verified hash and epoch write preconditions, preventing concurrent security changes from being overwritten. Reset remains bound to one claimed generation and advances both `passwordResetVersion` and `tokenVersion` exactly once in its successful User write.

## Password and epoch commit before session cleanup

Both password paths update `passwordHash`, `passwordChangedAt`, and `tokenVersion + 1` in one User operation; reset also clears lockout state and increments `passwordResetVersion`. There is no committed state containing the new hash and old epoch: a failure before the write preserves both old values, while a failure after it encounters the bumped epoch.

`revokeSessionsAfterEpochBump` then updates Session rows and records `SESSIONS_REVOKED` without touching the User. This prevents the double increment that calling the public method after the combined write would cause. A sweep failure still follows the generic API-error path, but occurs only after old credentials have become unusable.

## Public revocation and refresh races

`revokeAllSessions` still increments `tokenVersion` before sweeping and returns the sweep's `sessionsRevoked` count. Logout-all, completed refresh-token reuse, and suspended-account refresh still call it, preserving one epoch increment and the existing audit contract.

A refresh successor carries the claimed session's epoch and is checked against the User again before return. A password commit before that check retires the successor; a commit afterward sweeps it. If that sweep fails, access authorization and later refresh still reject it against the atomically bumped User epoch.

## Change-password CAS and reset generations

Change-password updates only while the account remains active and both the selected hash and `tokenVersion` still match. Two requests that verified the same password cannot both commit, and a concurrent reset or revocation changes at least the epoch, yielding the customer-safe `SESSION_EXPIRED` response instead of overwriting newer state.

Reset's claim remains single-use and generation-bound. Its User update requires the claimed generation and increments `passwordResetVersion` with the hash, so a newer reset request prevents an older claimed token from changing the password. Successful completion adds one reset-generation increment beyond the deliberate increment for each reset intent; the helper adds no generation or epoch mutation.

## Audit attribution and API errors

The private sweep receives the same actor and request context previously passed through `revokeAllSessions`, recording the same action, target, reason, and modified count. Actor normalization consumes only User id and role, so stale credential fields do not affect attribution or enter metadata.

CAS conflicts expose only `SESSION_EXPIRED` with sign-in-again copy, while reset conflicts remain `INVALID_RESET_TOKEN`. Unexpected persistence errors use the generic internal-error response; reset tokens, hashes, database errors, and internal metadata remain absent from API output.

## Coverage exercised

The targeted auth and audit suites passed 65 tests covering reset and change behavior, access invalidation, refresh rotation and reuse, bulk-revocation races, logout semantics, and audit events. Coverage includes a gated refresh-versus-bulk-revocation interleaving and concurrent reset consumption; change-password CAS interleavings were additionally traced through the conditional User write predicates.
