## Password commits establish invalidation before Session cleanup

`resetPassword` conditionally updates the active User at the claimed reset generation, setting `passwordHash` while incrementing `passwordResetVersion` and `tokenVersion`. `changePassword` requires the active User, verified `passwordHash`, and selected `tokenVersion` to remain current before replacing the hash and incrementing the epoch. A concurrent reset, password change, suspension, or bulk revocation therefore makes a stale writer fail instead of overwriting newer security state.

Both password paths call the private `revokeSessionsAfterEpochBump` after the combined User update; that helper cannot increment the epoch. Public `revokeAllSessions` still increments `tokenVersion` before sweeping, so password flows cannot double-increment while logout-all, suspended-account handling, and refresh-token reuse retain their independent epoch bump.

If Session cleanup fails, access authentication rejects the old token version and refresh checks the claimed epoch before successor creation and before returning it. A losing refresh is rejected or has its successor retired, so stale Session rows do not preserve usable credentials. These properties are **confirmed** from the changed service and unchanged authentication middleware.

Vite 6.4.3 declares Node `^18.0.0 || ^20.0.0 || >=22.0.0`, covering the backend's complete `node >=20` contract; the previous **confirmed** medium blocker is resolved.
