# Task 50 database invariants and production query indexes

Task 50 strengthens authentication epoch changes, makes provider-event receipts append-only at the model boundary, and adds deterministic pagination and reconciliation indexes across seven persisted domains. The refresh-token change closes the pre-`replacedBy` replay race by treating every `ROTATED` predecessor as reuse, while password changes now invalidate credentials in the same user-document write as the new password. Payment-event mutation guards cover the model operations that could rewrite or remove an existing receipt. Two valid customization list filters still lack indexes capable of producing their required sort order, so the database-design pass is not ready to ship.

Watch for: **confirmed** blocking sorts remain for status-only custom-request administration and payment-status-only custom-order administration because unbound fields sit between each filter prefix and the pagination sort keys.

**Verdict**: NEEDS_CHANGES

## High-level view

Refresh reuse now treats the atomic `ROTATED` claim itself as sufficient evidence, rather than waiting for `replacedBy`. Epoch-first account revocation and the winner's post-insert epoch check cover both sides of the sweep: a successor inserted after the sweep fails its epoch check, while one checked before the bump is caught by the following sweep.

Payment events remain insertable through normal creation paths but existing rows cannot be saved, updated, replaced, deleted, or mutated through `bulkWrite` on the model. This preserves provider events as evidence without changing the current transactional insertion path.

The notification, review, support, and media indexes align tie-break sorts with their query prefixes. **Confirmed:** the customization indexes cover unfiltered, priority, type, category, production, fulfillment, and completion views, but omit direct sorted indexes for status-only custom-request and payment-only custom-order filters.

## ROTATED refresh replay closes the pre-successor-link race

The failed single-use claim now checks only `revokedReason === ROTATED`; `replacedBy` is no longer a gate for account-wide reuse response. Revocation increments `User.tokenVersion` before sweeping active sessions. If the winning refresh inserts after that sweep, its post-insert epoch read revokes the successor; if it completes the read before the bump, the subsequent sweep catches the active successor. After both concurrent requests settle, no active session remains and outstanding access tokens carry the stale epoch, so the supplied standalone expectation of one surviving winner is stale rather than a production regression.

Password reset and authenticated password change update the password hash and `tokenVersion` atomically, then use cleanup that does not bump the epoch a second time. The authenticated path also compare-and-sets the prior hash and epoch, preventing concurrent security mutations from silently overwriting each other.

## PaymentEvent is append-only through the Mongoose model surface

The schema rejects existing-document saves and query-shaped updates, replacements, and deletions, including operations reached through `findOneAndUpdate` and `findOneAndDelete`. Document deletion is explicitly covered, and the compiled model's `bulkWrite` is blocked so bulk mutations cannot bypass schema middleware. First-save insertion remains available to the existing payment transaction.

## CustomRequest status filtering cannot use the requested sort

**Confirmed:** `adminCustomListSchema` accepts `status` without `priority`, and `listAdmin` always sorts by `{ createdAt: -1, _id: -1 }`. The only status-leading index is `{ status: 1, priority: 1, createdAt: -1, _id: -1 }`; when priority is unbound, MongoDB cannot use the later keys to provide the global creation-time order. A status-only admin request therefore performs a blocking sort. Add `{ status: 1, createdAt: -1, _id: -1 }` to `customRequest.model.js`; retain the status-plus-priority index for the combined filter.

## CustomOrder payment filtering has the same prefix gap

**Confirmed:** `adminCustomOrderListSchema` permits `paymentStatus` independently, while `listAdminOrders` uses the same creation-time pagination sort. `{ paymentStatus: 1, productionStatus: 1, fulfillmentStatus: 1, createdAt: -1, _id: -1 }` cannot provide that sort unless both intervening axes are constrained. Add `{ paymentStatus: 1, createdAt: -1, _id: -1 }` to `customOrder.model.js`; retain the wider index for the combined payment, production, and fulfillment filter.
