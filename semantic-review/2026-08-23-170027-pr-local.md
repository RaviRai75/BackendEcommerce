# Task 51 backend service and middleware boundary extraction

Task 51 moves recommendation ranking, request metadata projection, mock-webhook authentication, cache/idempotency policy, and repeated Mongo transaction mechanics behind explicit service or middleware boundaries. Controllers now project transport-neutral context before calling application services, while routes retain authentication, throttling, parsing, and validation order. Public catalogue behavior, webhook trust sequencing, and domain-specific transaction policies are preserved. No Task 51 regression or blocking architecture concern remains.

Watch for: No blocking concern; the recommendation dependency is one-way and does not form an import cycle.

**Verdict**: APPROVED

## High-level view

Recommendation selection now has its own service entry point and reuses an explicit product eligibility/DTO boundary. Public filtering, candidate shortlisting, scoring, deterministic ordering, and response shape remain unchanged without a reverse dependency from `product.service.js`.

Controllers lazily project a frozen plain request context. The projection keeps the former route-relative, query-free audit path, bounds IP and user-agent values, and prevents an Express request from entering changed application-service calls.

Mock webhook authentication is exposed by `paymentService` rather than a concrete adapter import in the route. Signature verification still consumes captured raw bytes before schema validation or parsed payload trust.

Private cache and idempotency policies are shared middleware at their former route positions. Product administration retains earlier no-store coverage for CORS, parsing, limiting, and route failures.

Order fulfillment, exchange administration, and support delegate transaction mechanics to one utility while retaining local reconciliation and error policy. Retry, ambiguity, abort, and cleanup behavior matches the removed copies.

## Recommendation ranking behind a one-way catalogue boundary

The source product and every candidate still require `PUBLISHED` status plus `publicRelationConstraint()`, keeping draft products and products attached to private taxonomy out of the result. Candidate pools remain capped at 200; relation-first shortlisting, merchandising fallback, category/collection/colour/occasion/fabric/price scoring, and final tie-breaks are unchanged.

Hydration restores aggregation order and maps through the same allow-listed `publicSummary` used by catalogue reads. `product.service.js` exports only `publicRelationConstraint` and `publicSummary` through `productRecommendationBoundary` and does not import the recommendation service. The resulting `recommendation.service.js -> product.service.js` edge is acyclic, and the app plus both modules load successfully.

## Frozen service context at the controller edge

`requestId` exposes `req.serviceContext` as a non-enumerable, non-configurable getter, projecting only request ID, compatibility ID, bounded IP address, bounded user agent, method, and bounded `req.path`. Headers, cookies, body, params, query, response state, and request methods do not cross the boundary.

Projection occurs inside the mounted router, preserving the former route-relative `req.path`. A nested-router smoke check returned `/probe` for `/api/probe?token=secret`; the API prefix and query were absent. `trust proxy` remains configured before projection, and both projection and audit normalization bound retained client metadata.

Changed controllers pass `req.serviceContext`, not `req`, into application services. `auditService` accepts that plain projection while retaining normalization for middleware-originated events; boundary searches found no Express-only request APIs in application-service modules.

## Raw-byte webhook authentication through paymentService

The route calls `paymentService.authenticateMockWebhook`, which delegates to the same `mockPrepaidAdapter.verifyWebhookSignature` implementation. Application assembly captures `rawPaymentWebhookBody` in the JSON parser’s `verify` callback; route authentication then runs before `validate({ body: mockWebhookSchema })`. `handleWebhook` receives authenticated signature data, parsed payload, and transport-neutral context separately, and no route imports the concrete adapter.

## Shared cache and idempotency policy without route-order drift

`privateNoStore` centralizes `Cache-Control: private, no-store`. Existing route-level placements remain ahead of authentication where they cover authentication and validation failures. Product/category/collection/media administration uses the early path-scoped app policy; segment-aware prefix matching covers pre-router failures without matching similarly prefixed public paths.

`requireIdempotencyKey` invokes each route’s existing Zod schema, stores only parsed data, stops on failure, and emits the same validation detail and default message. Authentication and limiters remain before it, while body and parameter validation remains after it across order, exchange, payment, review, product import/stock, customization, and support mutations.

## Shared transaction mechanics with local domain reconciliation

`runMongoTransaction` preserves five transaction attempts, five commit attempts, three reconciliation reads, linear backoff, snapshot read concern, and majority write concern. Transient transaction errors retry the whole transaction; unknown commit results retry commit, perform bounded reconciliation, then fail through the caller’s ambiguity factory rather than replay uncertain work. Non-ambiguous failures abort active transactions, and every attempted session is ended.

Order fulfillment, exchange administration, and support retain their own reconciliation queries, public service-unavailable messages, and transaction-support mapping. The utility imports no domain module; callers supply `work`, `reconcile`, and their ambiguity error constructor.
