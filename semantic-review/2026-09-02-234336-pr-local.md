# Dedicated administrator sign-in boundary

This change separates customer and administrator authentication into `/auth/login` and `/auth/admin/login`, adds a dedicated `/admin/login` page, and constrains post-login navigation to administration routes. Stored-role validation happens before session creation and cookie emission, while both entry points retain shared validation, rate limiting, lockout, and generic error responses. The role-mismatch path now performs the same failed-login audit, atomic attempt increment, and lockout work as a wrong password, resolving the previous audit gap and timing divergence. No concrete release blocker remains in the reviewed diff.

Watch for: **confirmed** the role-mismatch fix has no direct cross-role endpoint regression test; **confirmed** `safeAdminReturnTo` and its guarded return-state behavior still lack direct tests.

**Verdict**: APPROVED

## High-level view

The backend controllers pass `USER` or `ADMIN` into one shared login service. Password, account-state, and role checks complete before refresh-session persistence, token signing, or authentication-cookie creation, so correct credentials cannot cross the endpoint boundary.

A verified credential at the wrong entry point now calls `recordFailedLogin` with `wrong_entry_point`. This gives the attempt the same administrator audit, account write, threshold handling, and generic response as a wrong password; the paths differ only in the internal audit reason.

The frontend sends anonymous protected-admin visits to `/admin/login` with an internal `returnTo`. `safeAdminReturnTo` accepts only `/admin` and descendants, rejects `/admin/login` itself, and inherits the existing same-origin and malformed-path defenses.

**Confirmed:** focused validation does not directly exercise either cross-role endpoint/account combination or the new admin-only return-path policy. Code inspection found no failing behavior behind those non-blocking coverage gaps.

## Role gating before refresh-session and cookie issuance

`login` and `adminLogin` invoke the shared service with `USER` and `ADMIN`. The mismatch exit follows password verification but precedes the successful user update, `issueSession`, token signing, and `completeAuthentication`; a wrong-role request cannot persist a refresh session, return an access token, or emit refresh and CSRF cookies. The role comes from the stored user rather than a client assertion.

## Wrong-entry attempts now share failed-login security work

The mismatch branch calls `recordFailedLogin(user, req, "wrong_entry_point")` before returning `INVALID_CREDENTIALS`. That helper records `ADMIN_LOGIN_FAILED` for administrator accounts, atomically increments `failedLoginAttempts`, applies the existing threshold and lock duration, and records the lock transition. The wrong-password branch calls the same helper after the same password-hash verification, resolving the previous missing audit and skipped database work.

The remaining distinction is the internal audit reason, `wrong_entry_point` instead of `wrong_password`; it is not returned to the caller. No session or cookie issuance is reachable from either failure path.

## `/admin/login` return flow stays inside administration

```text
anonymous /admin/...   -> /admin/login + admin returnTo -> sanitized /admin/...
customer /admin/...    -> /account
admin /admin/login     -> sanitized admin returnTo or /admin
```

`safeAdminReturnTo` applies the existing internal-path sanitizer, then permits only `/admin` or `/admin/...` and maps `/admin/login` to `/admin`. External URLs, customer paths, malformed encodings, and a post-login self-loop fall back to the admin dashboard. `AdminPublicOnlyRoute` uses the same sanitizer for an already-authenticated administrator, while authenticated customers are sent to `/account`.
